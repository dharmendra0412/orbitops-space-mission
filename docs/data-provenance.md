# Data provenance and source integration plan

## Product rule

ORBITOPS must not fabricate measurements, mission telemetry, orbital states, spacecraft performance, or NASA observations. A value is displayed as a sourced observation only after the underlying product has been retrieved and its metadata parsed. If a value is unavailable, the interface must say **Not available from an integrated source**.

The source catalogue in `src/data/sources.ts` is a list of external references only. The FastAPI backend provides read-only PDS metadata search, product resolution, and hierarchy browsing. A separate, explicitly scoped validation workflow downloads and verifies one fixed LOLA GDR sample for engineering checks; the web application itself does not bulk-download, cache, or synchronize observation files. The PDS API documentation warns that its servers are not fully populated with all PDS datasets, so API search results must be cross-checked against the mission-specific archive index and direct archive holdings.

## Selected LOLA collection scope

The NASA PDS catalogue currently exposes two useful but different LOLA RDR collections:

- **Gridded collection** — LIDVID `urn:nasa:pds:lro_lola_rdr:data_gridded::1.0`. The PDS collection page describes it as a derived gridded-data collection. A PDS catalogue search snapshot indexed 16 October 2026 reported 561 collection members.
- **Calibrated collection** — LIDVID `urn:nasa:pds:lro_lola_rdr:data_calibrated::17.0`. The PDS catalogue snapshot indexed 16 October 2026 reported version 17.0, updated for LRO Release 67, and 75,626 collection members.

These counts and versions are catalogue snapshots, not live counters embedded in ORBITOPS. The gridded collection is the bounded starting point for understanding map-oriented products; the much larger calibrated collection should be sampled by a documented query rather than bulk-downloaded. Always resolve the current product label and collection membership from PDS before ingesting.

### ### Resolved LOLA GDR height and polar-grid conventions

The selected product label declares `IMAGE.NAME = HEIGHT`, `SAMPLE_TYPE = LSB_INTEGER`, `SAMPLE_BITS = 16`, `SCALING_FACTOR = 0.5`, and `OFFSET = 1737400.`. The product-family interpretation is supported by two matching authoritative references:

- The [LOLA RDR/GDR Software Interface Specification, section 5.4](https://pds-geosciences.wustl.edu/lro/lro-l-lola-3-rdr-v1/lrolol_1xxx/document/rdrsis.htm) gives a GDR example in the same `LRO-L-LOLA-4-GDR-V1.0` data set, product version V2.0, with the same `IMAGE.NAME = HEIGHT`, signed 16-bit little-endian samples, scaling factor 0.5, and offset 1737400 m. Its explicit conversion note defines `HEIGHT = DN * SCALING_FACTOR`; it separately defines `PLANETARY_RADIUS = DN * SCALING_FACTOR + OFFSET`. It also states that planetopotential topography requires subtracting a geoid radius.
- The [PDS Orbital Data Explorer GDRDEM reference](https://ode.rsl.wustl.edu/MArs/pagehelp/Content/Missions_Instruments/Lunar%20Reconnaissance%20Orbiter%20(LRO)/LOLA/GDR/GDRDEM.htm) independently repeats the same distinction for LOLA GDRDEM products.
- The [PDS Geosciences Node FAQ](https://pds-geosciences.wustl.edu/missions/lro/lola_faq.htm) gives a generic formula that adds OFFSET to HEIGHT. That statement conflicts with the GDR-specific SIS and GDRDEM documentation above; ORBITOPS records the discrepancy but follows the more specific GDR product definition. OFFSET is not added to HEIGHT.

Accordingly, the documented conversions for this GDR product family are:

- Height/elevation relative to the reference sphere: `HEIGHT_m = DN * 0.5`.
- Planetary radius: `RADIUS_m = DN * 0.5 + 1,737,400`.
- Planetopotential topography is not derivable from this raster alone; it additionally requires a matching geoid-radius model and reference.

The official [DSMAP_POLAR.CAT](https://pds-geosciences.wustl.edu/lro/lro-l-lola-3-rdr-v1/lrolol_1xxx/catalog/dsmap_polar.cat) supplies the authoritative polar stereographic equations and pixel-center convention for data set `LRO-L-LOLA-4-GDR-V1.0`. It explicitly defines `I = sample`, `J = line`, `NS = -1` in the southern hemisphere, `X = (I - N/2 - 0.5) * MAP_SCALE`, `Y = (J - N/2 - 0.5) * MAP_SCALE * NS`, `R = sqrt(X^2 + Y^2)`, `LON = atan2(X,Y) * 180/pi`, and `LAT = -90 + 2*atan(0.5*R/1737400) * 180/pi`. The implementation uses the sample displacement for X and the sign-reversed line displacement for Y. Regression tests assert all four quadrants, guarding against swapped axes and incorrect southern-hemisphere orientation. The catalog also records the expected visual convention: longitude 0 extends upward from the south-pole map center and longitude 90 east extends to the right.

A further geodetic software check has been added to `backend/scripts/validate_lola_jp2_reference.py`: PROJ transforms eight pixel-center coordinates from the JP2-declared stereographic CRS into a spherical lunar geographic CRS, and the resulting latitude/longitude values are compared with the PDS DSMAP_POLAR equations. The sample set covers the four center-adjacent quadrants plus edge/corner locations; longitude differences are normalized across the 0/360-degree wrap. The gate uses a 1e-7-degree tolerance. This validates consistency between the JP2 CRS/affine transform and the PDS pixel-center equations, but does not establish independent geodetic truth or independently realize the DE421 frame. The new check passed against the actual archived JP2 in GitHub Actions run [#43414069534](https://github.com/dharmendra0412/orbitops-space-mission/actions/runs/43414069534), step 9. All eight sample pixels passed the 1e-7-degree tolerance; maximum latitude discrepancy was 5.3219651e-11 degrees and maximum wrapped-longitude discrepancy was 0 degrees. This projection pass does not independently establish geodetic ground truth or the DE421 frame realization.

The web workspace now includes a source-label-driven pixel coordinate lookup. After retrieving the PDS3 label, a user can enter zero-based line and sample indices to calculate planetocentric latitude, east longitude, and projected X/Y using the same DSMAP_POLAR fields. The browser module has regression tests for all four quadrants, pixel-center offsets, bounds, invalid numeric values, and reference-frame rejection. It does not read the IMG raster or return a DN/elevation value; raster serving and terrain visualization remain separate future work.

## Live discovery endpoint

The FastAPI service exposes:

- `GET /api/v1/pds/search?keywords=LOLA&limit=10` — forwards a keyword query to the NASA PDS Search API.
- `GET /api/v1/pds/products/{identifier}` — resolves a PDS product LID/LIDVID.
- `GET /api/v1/pds/products/{identifier}/members?depth=1|2&limit=100&search_after=...` — browses a page of child collections/products and supports source-defined cursor pagination.
- `GET /api/v1/pds3/lola/gdr/ldem-85s-40m/label` — retrieves one fixed public PDS Geosciences Node label and parses allowlisted PDS3 metadata fields.
- `GET /api/v1/pds3/lola/gdr/ldem-85s-40m/pixel?line_index=...&sample_index=...` — validates that label, then requests exactly two bytes from the fixed IMG URL and returns the original signed DN plus label-derived height/radius and PDS polar coordinates.
- `GET /api/v1/pds3/lola/gdr/ldem-85s-40m/profile?line_index=...&start_sample_index=...&sample_count=...` — retrieves a bounded contiguous row segment (maximum 512 samples) from the same fixed IMG URL and returns original DN values with source-label-derived height/radius, polar coordinates, and validated metres-per-pixel spacing.

The search request asks for the `application/kvp+json` representation and the documented summary fields `lidvid` and `title`. Hierarchy pages are limited to 100 records per request and sorted by the PDS harvest timestamp; the next-page cursor is exposed only when the last returned source record supplies that field. The search endpoint returns the upstream JSON unchanged under `response`, plus the exact request URL, search parameters, and retrieval timestamp. Product resolution requests `application/vnd.nasa.pds.pds4+json` so the response can include the full PDS4 label translation and registry metadata (including file references and checksums when supplied by PDS). Hierarchy browsing uses `application/json` and preserves the returned child-product records. It does not download the linked product files, invent a result when the API returns none, or claim that all PDS archives are indexed. A successful metadata search is discovery only, not dataset ingestion.

The fixed LOLA label endpoint refuses redirects, limits the response to 1 MB, requires ASCII text, and uses a static archive URL rather than accepting a caller-supplied URL. It returns raw metadata strings and units. The pixel endpoint validates the source label against the fixed 7584 × 7584, 16-bit little-endian product contract, computes the byte offset from the requested zero-based line/sample indices, and issues a fixed-origin HTTP Range request for exactly two bytes. It requires HTTP 206, the exact expected Content-Range, and a two-byte body; a server that ignores Range is rejected without reading its full response. The original DN is decoded as signed little-endian 16-bit data; height and planetary radius use the source label's GDR scaling/offset; coordinates use the documented DSMAP_POLAR projection fields. This is a one-cell source lookup or a bounded one-row profile, not a terrain tile, a complete raster integrity check, or independent geodetic ground truth. The profile UI plots the returned source samples without interpolation or smoothing.

## Bounded live LOLA pixel reads

The web application exposes a small source-backed pixel lookup after the user retrieves the fixed PDS3 label. It accepts zero-based line and sample indices only. The backend computes the two-byte offset from the validated fixed product layout (7,584 samples per row, 15,168 bytes per record) and requests exactly that range from the fixed PDS Geosciences IMG URL. It refuses redirects, HTTP 200 responses that ignore Range, unexpected Content-Range values, and bodies other than exactly two bytes. The endpoint does not accept arbitrary URLs, read a full raster, or cache observations.

The API returns the original signed DN and separately labelled derived fields: GDR HEIGHT = DN × SCALING_FACTOR and PLANETARY_RADIUS = DN × SCALING_FACTOR + OFFSET. Latitude/longitude are computed from the same retrieved label's projection metadata and the PDS DSMAP_POLAR equations. The response includes the original raster URL, label URL, retrieval time, byte offsets, units, and coordinate reference frame.

The source-validation workflow probes the actual archive with exact two-byte range requests after the full IMG has been downloaded and validated. `scripts/validate_lola_http_range.py` checks center-adjacent pixels, all four central quadrants, and image-edge locations; every returned byte pair must match the corresponding bytes in the fully validated local IMG. The probe report is included in the workflow artifact. Unit tests cover ignored ranges, malformed Content-Range values, truncated/oversized bodies, signed decoding, non-zero byte offsets, and mismatch against the validated local source. Passing this range check establishes only that the selected archive supports the bounded-read contract; it does not prove geodetic accuracy.
The complete source-validation workflow passed with the live API range methods in run [#43416474484](https://github.com/dharmendra0412/orbitops-space-mission/actions/runs/43416474484). It performed eight two-byte pixel reads at center/quadrant/edge positions and one contiguous eight-sample row-profile read; every decoded result matched the corresponding bytes in the fully downloaded and validated IMG. The same run passed full-raster sample-count/extrema validation, the complete IMG-versus-JP2 decoder comparison, the eight-point PROJ/PDS pixel-center check, and the bounded Haworth regional cross-product comparison. Its retained source and reports are in artifact [#14031861899](https://github.com/dharmendra0412/orbitops-space-mission/actions/runs/43416474484/artifacts/14031861899) (30-day retention). The range-validation script exercises the same fixed-source PdsClient methods used by the live pixel and row-profile endpoints.

## Independent geodetic validation research

A separate optical stereo product is not automatically independent geodetic truth. The [USGS LROC NAC South Pole DEM verification and validation report](https://astrogeology.usgs.gov/search/map/moon_lro_south_pole_dem_verification_and_validation_report) describes a 4 m/pixel LROC stereo DEM whose image registration was tied to the LOLA 5 m DEM; it reports remaining 1–5 m seams between stereo models and potential errors in shadow/edge regions. This is useful cross-sensor surface-shape evidence, but it is not an independent absolute control network for the LOLA-derived product.

The [USGS description of LROC NAC stereo DTMs](https://www.usgs.gov/publications/extracting-accurate-and-precise-topography-lroc-narrow-angle-camera-stereo) explains that these DTMs are registered to LOLA profiles to improve absolute accuracy. The [LROC positioning best-practices paper](https://doi.org/10.3847/psj/ad54c6) likewise describes controlled NAC DTMs as tied to GRAIL-corrected LOLA tracks. A Kaguya Terrain Camera DEM is also not independent if it is co-registered to LOLA; the [SLDEM2015 paper](https://doi.org/10.1016/j.icarus.2015.07.039) explicitly describes that co-registration.

The live API label client has also been exercised against the actual archive in [full source-validation run #43423371997](https://github.com/dharmendra0412/orbitops-space-mission/actions/runs/43423371997). The same `LaltClient.fetch_gt_sp_label` method used by the API returned all 3,938 label bytes, matching the independently downloaded validation label byte-for-byte with SHA-256 `fbd124c0e524a6a5c495a1c77033db9f7ca699125ad2bcf48b331fd8f2fac01d`. The validated TI range is 883526397–883538438, with 40 missing integer ticks between successive records. The `LALT_ALTITUDE` range field spans 82,367.0–113,596.9 m in this day file. These are source-column extrema, not a geolocated lunar surface-height range.

The calibrated range archive also publishes daily `LALT_RD_YYYYMMDD.TAB` products. The official 2008-01-05 example label identifies `SLN-L-LALT-3-RANGE-V1.0`, `LALT_RD_20080105`, 12,002 table rows, 11 ASCII columns, and 162-byte fixed records. Its first column is the SELENE main-orbiter internal clock count (`TI`); the second is `LALT_ALTITUDE` in metres, followed by return-peak, output-power, APD-voltage, temperature, PPS, start-mode, and threshold telemetry. The example label reports `START_TIME` and `STOP_TIME` as `UNK`; its clock tags therefore must not be treated as UTC. The product description documents thermal correction of the timer and a range precision within ±5 m, but the daily range table itself contains no surface latitude/longitude. The new source-validation step downloads the fixed 2008-01-05 label/table, checks the PDS byte and row layout, validates all 12,002 records and numeric fields, and records local SHA-256 provenance. It deliberately stops before TI-to-ET conversion or geolocation.

A separate instrument candidate exists in Kaguya's Laser Altimeter (LALT) archive. The calibrated range dataset is PDS3 `SLN-L-LALT-3-RANGE-V1.0` (DARTS identifier `darts:sln-l-lalt-3-range-v1.0`); the archive reports temporal coverage 2007-12-30 to 2009-06-10 and range precision within ±5 m. JAXA publishes a separate `LALT_SP.txt` south-pole grid above 85°S on a 1/64° grid, using observations from 2007-12-30 to 2008-03-31; void cells are encoded as -99 and JAXA terms of use apply. This is not the same file as the PDS3 `SLN-L-LALT-5-TOPO-GT-SP-IMG-V2.0` dataset. The actual detached PDS3 label for `LALT_GT_SP_IMG.IMG` (`SLN-L-LALT-5-TOPO-GT-SP-IMG-V2.0`) resolves important format ambiguities: it declares 11,520 × 1,408 pixels, 32-bit `PC_REAL` (little-endian) samples, 64,880,640 data bytes, a regular latitude/longitude grid with pixel-node registration (MAP_PROJECTION_TYPE=N/A), 1/128° latitude and 1/32° longitude spacing, grid nodes from -79.00390625° to -89.99609375° latitude and 0.015625° to 359.984375° east longitude, elevations in km on a 1,737.4 km sphere, `MEAN EARTH/POLAR AXIS OF DE421` body-fixed coordinates, and 99.999 as the dummy value. The label's center and projection-offset fields are retained for provenance; the grid's published coordinates should be read from the label's latitude/longitude bounds and pixel spacing, not treated as a polar-stereographic image. The label comment says this image is derived from `LALT_GT_SP_NUM`, itself generated from `LALT_LGT_TS` by spherical interpolation, with elevations rounded to 0.001 km. The `LALT_LGT_TS` label explicitly describes SPICE-derived geolocated time-series data using LALT range, main-orbiter position/attitude, UTC, DE421, Mean Earth/Polar Axis coordinates, and the same 1,737.4 km sphere. Its format example names an SGM100g / NAOJ_RISE orbit file; the exact orbit kernel used for the selected grid must still be verified. These products are promising independent-altimeter cross-sensor evidence, but the interpolated grid is not raw measurement data and is not itself ground truth. These are promising separate-instrument comparison candidates, but each selected product's actual label, orbit file, datum, frame, grid registration, and uncertainty must be checked before use. The JAXA 1/64° grid and PDS3 1/128° × 1/32° grid must not be treated as the same product or compared to the 40 m LOLA grid as if resolutions were equivalent. However, geolocation of derived LALT topography depends on the spacecraft orbit solution. NASA GSFC's [improved Kaguya orbit product](https://pgda.gsfc.nasa.gov/products/74) explicitly adjusts LALT tracks to fit a LOLA/TC basemap, so that improved solution is tied to LOLA and cannot serve as independent absolute control. JAXA's official [SELENE SPICE kernel archive](https://darts.isas.jaxa.jp/en/datasets/darts:sln-l-spice-6-v1.0/) provides the navigation ancillary products needed to reconstruct geometry, including SPK ephemerides, CK attitude, FK/IK definitions, SCLK, LSK, and lunar PCK files. Its published inventory lists mission SPKs such as `SEL_M_071020_081226_SGMI_05.BSP` and `SEL_M_071020_090610_SGMH_02.BSP`; however, the LALT_LGT_TS format example names `NAOJ_RISE_MAIN_ORBIT_SGM100g_20071020_0000-20081029_1338.bsp`, which is not the same filename. The archive's existence therefore does not yet establish which precise orbit kernel generated each LGT time-series day. Its `spkinfo.txt` is especially important: the `SEL_M_071020_081226_SGMI_05.BSP` orbit solution uses tracking and laser-altimeter crossovers for January and March 2008 (reported crossover RMS 23.61 m and 23.47 m, respectively), so it is not independent LALT control for those arcs. The `SEL_M_071020_090610_SGMH_02.BSP` orbit solution is documented as using two-way tracking only, with no 4-way data in the orbit determination (although 4-way tracking contributed to the gravity-field model); its stated coverage is 2007-10-20 to 2009-06-10, with documented gaps and arc-boundary jumps, and the archive reports radial overlap errors of at least 3 m with larger outliers possible. SGMH is therefore a candidate independent-of-LALT orbit solution for selected raw-range reconstruction intervals, not yet a validated absolute control solution. The LGT example still names a different SGM100g orbit file, and the exact daily product mapping remains unresolved. The kernel chain needed to test a raw-range reconstruction is now identified, but has not yet been executed against the 2008-01-05 records. The official archive provides `SEL_M_V01.TSC` for onboard clock-to-ET conversion; its 2022-03-07 release note says version N0067 corrects `SCLK01_OFFSETS_131`, so older SCLK versions must not be substituted. It provides the January 2008 `SEL_M_200801_D_V03.BC` CK (2-second telemetry-derived attitude; V03 corrected the angular-velocity reference to J2000), `SEL_V01.TF` spacecraft frames, and `SEL_LALT_V01.TI` LALT instrument geometry (NAIF ID -131501, platform -131000, boresight approximately +Z, 0.0002 rad FOV half-angle). The lunar frame chain for the product's Mean Earth coordinates is `moon_080317.tf` + `moon_assoc_me.tf` + `moon_pa_de421_1900-2050.bpc` + `pck00010.tpc`; `de421.bsp` supplies the planetary ephemeris, and the current NAIF `naif0012.tls` is the leap-seconds kernel reference for UTC conversion. The SPK candidate is `SEL_M_071020_090610_SGMH_02.BSP`, not the SGM100g orbit file named in the LGT example. The SGMH information file says its orbit solution uses two-way tracking only (4-way tracking contributes to the gravity-field model); its arc coverage, CK coverage at each converted ET, frame IDs, attitude gaps, and ray-intersection geometry still require executable checks. The LALT IK defines instrument pointing, but no surface location can be claimed until the SCLK conversion, SPK/CK coverage, frame chain, and measured-range intersection are validated. The next provenance task is to retrieve the relevant daily LALT_LGT_TS and LALT_RD labels, resolve the exact orbit file and version, inspect SPICE coverage/frame IDs/time system, and document whether the selected orbit solution used any LALT crossovers or other altimetry constraints. The original calibrated LALT range archive remains a candidate for a separately labelled cross-sensor comparison only after its archived orbit, time system, frame, and uncertainty are independently characterized. A real-source cross-product run completed in [GitHub Actions run #43421295441](https://github.com/dharmendra0412/orbitops-space-mission/actions/runs/43421295441), with the full IMG, label, and comparison report retained in [artifact #14034980288](https://github.com/dharmendra0412/orbitops-space-mission/actions/runs/43421295441/artifacts/14034980288). The downloaded LALT label was 3,938 bytes (local SHA-256 `fbd124c0e524a6a5c495a1c77033db9f7ca699125ad2bcf48b331fd8f2fac01d`); the IMG was 64,880,640 bytes (local SHA-256 `a4e703a99dc2635c3506a9c00eb2c76cd33d786c3c30b0e6785a6e96d981e3cf`) and decoded as 16,220,160 float32 nodes. In the overlapping 85°S–90°S region, 7,372,800 valid LALT cells matched valid LOLA cells. Nearest-pixel residuals (LALT minus LOLA) had bias +2.3773 m, median +1.4053 m, MAE 15.8633 m, RMSE 23.8686 m, P95 absolute residual 50.3500 m, P99 84.4900 m, and maximum absolute residual 378.8569 m. Using a 3×3 LOLA-neighborhood median gave bias +2.3492 m, median +1.3830 m, MAE 15.7947 m, RMSE 23.8075 m, P95 50.2580 m, P99 84.3970 m, and maximum absolute residual 379.8569 m. These residuals are not a pass/fail accuracy score: they reflect different spatial resolutions, interpolation, local slope, and orbit/geolocation uncertainty. They reinforce why the product is a qualified cross-sensor consistency source, not independent ground truth. See the [DARTS calibrated range dataset](https://darts.isas.jaxa.jp/en/datasets/darts:sln-l-lalt-3-range-v1.0/), [JAXA south-pole grid and readme](https://www.kaguya.jaxa.jp/en/science/LALT/The_lunar_topographic_data_e.htm), [PDS LALT calibrated products](https://ode.rsl.wustl.edu/moon2/pagehelp/Content/Missions_Instruments/KAGUYA%20%28SELENE%29/LALT/Calibrated_Data.htm), and [PDS LALT derived products](https://ode.rsl.wustl.edu/moon2/pagehelp/Content/Missions_Instruments/KAGUYA%20%28SELENE%29/LALT/Derived_Data.htm).

Accordingly, none of these products is currently accepted as independent geodetic ground truth for the selected PDS LOLA grid. They may support separately labelled cross-sensor morphology checks after product-specific coverage, datum, resolution, control method, and uncertainty are verified. An independent absolute validation gate remains open; no terrain accuracy claim or terrain rendering is enabled by the present decoder and cross-product checks.

## Integration requirements

Every imported product must preserve:

- Source agency, archive/node, dataset and collection identifier.
- Original product URL and persistent identifier/DOI where provided.
- Product version, release number, processing level, and retrieval timestamp.
- Observation/acquisition time and coverage interval.
- Original units, coordinate system/reference frame, datum, and time system.
- Instrument, target, geometry and quality flags where supplied.
- Original label/metadata files and checksum for downloaded files.
- Citation and applicable license/data-use statement.
- Transformation history: software/version, parameters, and output checksum.

Raw source files must remain distinguishable from derived products. Derived values must link back to their input product identifiers and transformation record.

## Planned data integration sequence

1. Implement an archive metadata catalogue and ingestion manifest; do not download bulk data before selecting specific product collections and coverage.
2. Start with the published LOLA RDR bundle (LIDVID `urn:nasa:pds:lro_lola_rdr::1.0`) and its gridded collection (LIDVID `urn:nasa:pds:lro_lola_rdr:data_gridded::1.0`). The PDS catalogue snapshot reports 561 gridded collection members; use that collection for a small, bounded sample. Keep the Release 67 calibrated collection (LIDVID `urn:nasa:pds:lro_lola_rdr:data_calibrated::17.0`, snapshot count 75,626) as a separate, larger source. Use the PDS Search API to resolve/search metadata, then cross-check against the direct LRO/LOLA archive because the Search API may not contain every holding. Parse the selected product's PDS label before rendering any elevation value.
3. Add selected LROC products with their original pointing/geometry metadata and source citations.
4. Evaluate Diviner products for thermal-context views, keeping the instrument's observation time and processing level visible.
5. Add SPICE kernels only if a later, explicitly approved engineering requirement needs geometry or ephemeris calculations. No orbit propagation or mission simulation is part of the current product scope.
6. Add independent validation cases and compare derived outputs against published product documentation before exposing them as calculated engineering values.
